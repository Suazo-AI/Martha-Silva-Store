3. “Registraba cero” significa que el sistema dice que no hay unidades.

No significa precio cero, venta gratis ni que falte dinero. Puede existir una prenda en la mano y que el registro esté desactualizado o que se haya elegido otra talla/bodega.

La decisión de entrega ya está tomada.

Si la prenda física existe, se entrega aunque el registro diga 0. Recomiendo confirmar SKU, talla y ubicación, y registrar una conciliación rápida con motivo y actor antes de descontar la venta.

La facultad de autorizar sigue pendiente. Mi recomendación es que la encargada tenga esa facultad operativa. La venta debe conservar la incidencia y su trazabilidad.

Buen visto: el coordinador comprueba que hubo una sola entrega, un solo cobro, movimientos +1/−1 enlazados y un saldo final correcto. El motivo no se borra ni se disfraza como una compra ficticia.

El ajuste y la venta deben protegerse frente a otra caja que intente vender la misma unidad. El modelo secuencial no demuestra esa atomicidad en SQL. Si no hay prenda física, no se promete una entrega inexistente.

6. CI verde significa que ciertas comprobaciones pasaron.
CI es el proceso que GitHub ejecuta cuando cambia el código. La pregunta pendiente es qué debe bloquear una integración y con qué evidencia. Un color verde por sí solo no prueba que estén todas las pruebas necesarias.


Lo que existe
El candidato histórico 53dd23b5 conserva 601 casos backend aprobados. Hay pruebas de navegador y API/SQL. El verificador exige un mínimo de casos y que los presentes pasen.
Ese mínimo no demuestra que no se quitó una prueba crítica y se agregó otra para conservar el número. Los skips previstos de jobs no equivalen a casos backend omitidos.
Lo que recomiendo exigir
  1. Requisito → caso crítico obligatorio → resultado → SHA exacto.
  2. Pruebas sobre API, navegador y SQL reales con datos ficticios.
  3. Rechazar ausencia o skip de un caso obligatorio.
  4. Provocar fallos y demostrar que el control los detecta.
  5. Conservar artefactos revisables y proteger main con checks requeridos.


Ejemplo: si alguien hace que un doble clic cree dos ventas, la prueba debe fallar por dos documentos y doble stock. Si alguien borra esa prueba, el inventario de casos obligatorios también debe fallar. Así se comprueba tanto el producto como el control.
