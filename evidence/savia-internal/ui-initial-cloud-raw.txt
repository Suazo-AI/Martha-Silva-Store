## P1 disposition

The previous packet `f154959` remains superseded and unaccepted. In this candidate, `app.mjs:205–208` handles 401 after destroyed/epoch checks but **before** the per-section requestId check. `requireAccess` increments epoch, nulls app identity, clears private rows/identity, hides and inerts shell, and locks actions. This fixes the identified stale-request 401 bypass while still preventing old-session responses affecting a replacement session.

The new DOM regression starts two overlapping refresh reads, rejects the older with 401, verifies session closure and empty rows, resolves the newer success, and verifies no repopulation. It passes. The reverse completion ordering (newer success first, older 401 second) is covered by the source control flow, not a separate named executed test. No further P1 was found in this narrow delta review; this is not a claim that no other vulnerability exists.

## Remaining P2 and scope limits

- **P2 pagination still open:** `client.mjs:23–37` sends no skip/take and exposes no paging options; `index.html`/`app.mjs` have no page controls. Only the default first 50 customer/item results are browsable per query, though `X of total` is shown. Full-directory acceptance requires paging or explicit acceptance of this limitation.
- Only auth/session/logout and read-only customer/item queries are connected. Directory mutations, stock balances/adjustments, sales/cancellations/returns, PO/receipt workflows, staff management, stable business idempotency and operation reconciliation are absent/disabled. Supplier/location reads exist in the adapter but lack visible connected workflows. These omissions are honestly described in the interface, not fallback behavior; they still prevent claiming a completed SAVIA.
- Client-dialog field names are not a mutation DTO (`displayName`, `customerId` vs directory `{kind,name,...}`). It remains disabled, so this is not a live contract failure; the owner must adapt DTOs explicitly rather than blindly serializing it when writes are added.
